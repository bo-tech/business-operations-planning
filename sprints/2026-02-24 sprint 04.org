** Learnings and Insights

*** Caching / Data transfer

**** Issue

Fast iterations on the cluster bootstrap were pailful because of the re-download
of the container images. The Nix part for the frequent system rebuild was
unproblematic, cached in the local machine's nix store and on the microvm hosts'
stores as well.

Putting a cache per type of artifact is substantial work.

**** Squid cache as http proxy

Using squid cache as a http proxy with ssl mitm support did allow to capture
most of the traffic from container image blobs. A full re-deployment of the
empty acceptance cluster did use around 250 MB of traffic in total, without even
accounting for other unrelated traffic during the measuring period.

Only challenge is that many requests use signing via HTTP get parameters, so
that by default a cache would never hit.

Squid has helpers to do URL manipulation which did allow to solve this problem.

Long term it would be nicer to have a smarter caching setup, for now this is
good enough for anything http related.

*** Helm via Flux slows iteration

HelmRelease actions (install/upgrade) hold a lock for the full timeout duration
(15 minutes in our case). If something goes wrong mid-action, there is no way to
force-cancel it — suspend/resume only takes effect after the current action
finishes. The only workaround is deleting Helm's internal lock secret.

This makes the fast iteration cycle of "fix, push, observe" painful compared to
plain kustomize or Kluctl where applying is immediate and idempotent. Especially
during bootstrap and restore scenarios where rapid debugging is needed.

Reinforces the long-term preference for Kluctl.
