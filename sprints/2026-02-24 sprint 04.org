** Notes

** Learnings and Insights

*** Caching / Data transfer

**** Issue

Fast iterations on the cluster bootstrap were pailful because of the re-download
of the container images. The Nix part for the frequent system rebuild was
unproblematic, cached in the local machine's nix store and on the microvm hosts'
stores as well.

Putting a cache per type of artifact is substantial work.

**** Squid cache as http proxy

Using squid cache as a http proxy with ssl mitm support did allow to capture
most of the traffic from container image blobs. A full re-deployment of the
empty acceptance cluster did use around 250 MB of traffic in total, without even
accounting for other unrelated traffic during the measuring period.

Only challenge is that many requests use signing via HTTP get parameters, so
that by default a cache would never hit.

Squid has helpers to do URL manipulation which did allow to solve this problem.

Long term it would be nicer to have a smarter caching setup, for now this is
good enough for anything http related.

*** Helm via Flux slows iteration

HelmRelease actions (install/upgrade) hold a lock for the full timeout duration
(15 minutes in our case). If something goes wrong mid-action, there is no way to
force-cancel it — suspend/resume only takes effect after the current action
finishes. The only workaround is deleting Helm's internal lock secret.

This makes the fast iteration cycle of "fix, push, observe" painful compared to
plain kustomize or Kluctl where applying is immediate and idempotent. Especially
during bootstrap and restore scenarios where rapid debugging is needed.

Reinforces the long-term preference for Kluctl.

** Closing Status

Outcome:
- Full split of ~b-ops~ into ~business-operations~ (public) and ~b-ops~ (thin
  private overlay) completed.
- All base-apps and apps migrated, wired, and tested on acceptance cluster.
- Acceptance cluster fully deployed from the split setup.
- Project home moved to Codeberg (~business-operations~ org).

What works:
- ConfigMapGenerator pattern for Helm values extraction and site overlays.
- ADR-0022 kustomization.yaml at every level for flexible inclusion.
- Site overlay pattern with Flux Kustomization path patches.
- Caching proxy (ci-cache) dramatically reduces re-deployment bandwidth.
- VolSync backup/restore across production and acceptance clusters.
- Authelia with split access-control configuration (base + site overlay via
  ConfigMap key replacement).

What needs improvement:
- Caching proxy causes issues with the GitLab registry after roughly a day;
  apart from that it works very well.
- Authelia does not merge ~access_control~ across multiple config files;
  required restructuring to single-file approach with ConfigMap key override.
- Helm via Flux lock timeouts still slow iteration during debugging.

Key insights:
- Authelia loads config files alphabetically but replaces (not merges) sections
  like ~access_control.rules~. Site-specific overrides must replace the full
  section via a single file.
- ConfigMap hash suffixes with ~name-reference.yaml~ enable automatic pod
  restarts on config changes without manual intervention.
- The split surfaced several implicit configuration assumptions that needed
  explicit handling in the overlay pattern. Examples: a ~subPath~ volume mount
  that only exposed one ConfigMap key (hiding the site overlay file), and a
  single-file ConfigMap that needed to become a directory mount to support
  base + overlay config files.
